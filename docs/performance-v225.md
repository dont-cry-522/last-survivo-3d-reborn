# v225：首次战斗、连续游玩与离线交付

本轮从当前本地 v224 工作区冻结副本继续，只修改 REBORN，保留已有未提交工作。没有修改 NEXT、原版，没有提交、推送或发布。基线、真实浏览器记录和本轮增量补丁位于工作区 `outputs/reborn-stability-v225/`。基线是本轮开始时的脏工作区，不是 Git HEAD。

## 实际改变

- 进入战斗前准备当前地图怪物与首领的既有声音。沿用实际播放时的录音或生成样本，不提前播放，不改变音量、音色、冷却或随机顺序；其他地图不在此时准备。飞行怪物借用的声音与自身受击材质分别处理。缓存跨局复用，代价是首次进场的准备时间和音频内存。
- 补齐经验光点、现有技能粒子和蜃影替身的真实渲染准备。替身只为蜃影准备，复用快照缓冲；实际闪避仍捕捉当时的人物姿态，共享骨架每次只更新一次。准备结束或异常时恢复父级、显示状态、变换与材质参数，退出后释放快照。
- 场景准备结束、第一/第三人称切换后，恢复下一帧实际需要的灯光状态，避免人物阴影首次使用时临时编译不同程序。没有增加每帧全场景绘制。
- 当前 Three.js 将部分程序诊断和 Uniform/Attribute 查询延迟到首次使用。把这部分工作放进加载阶段分片执行，保留原错误检查和原生缓存，不改 vendor。真实 vendor 实现的单元测试覆盖失败恢复及缓存复用。
- 加载末尾通过 WebGL2 fence 等待已经提交的准备任务实际完成。非阻塞轮询，保持遮罩、输入锁和游戏时间不动；没有固定填充等待、`gl.finish` 或额外绘制。完成、失败均删除同步对象；设备上下文丢失、等待失败或超过 10 秒进入原有重试流程。
- 同一怪物的受击姿态恢复数据复用固定向量和四元数，避免逐帧分配临时对象。受击动作、持续时间和伤害不变。

没有增加依赖或下载模型、贴图、声音。画质档位、像素比策略、景物和敌人数量、碰撞、伤害、武器、地图、升级与存档规则不变。

## 为什么还要检查显卡准备

首轮候选虽然没有新增着色器程序，首战仍有 53–58 毫秒长任务。独立 CPU profile 把约 30.57 毫秒定位到 `getUniforms → onFirstUse → getProgramInfoLog`，因此进行了程序首次使用准备修复。

修复后，定向短测的首战 CPU 提交降到桌面 3.5 毫秒、手机尺寸 7.6 毫秒；但加载提示隐藏后，到下一次真实战斗帧仍等待约 0.4 秒。仅加两次 RAF 回调没有解决，已作为失败候选保留记录，不能将它称为最终修复。

随后使用同一 `/current` 资源基址做独立控制试验：不在开局读取 GL 错误时仍等待 312.7 毫秒；读取 `getError` 时为 317.7 毫秒，其中读取本身等待 282.3 毫秒。它不是单纯由测试工具额外制造的延迟。仅在加载结束加入异步 GPU fence 后，真实队列等待 320 毫秒、73 次非阻塞轮询；等待期间状态为 loading、游戏时间为 0。提示隐藏到首战帧降为 20.8 毫秒，首战 CPU 提交 5.2 毫秒。

这支持等待显卡完成已提交的准备任务，而非增加固定延时。该等待不是单帧 GPU 耗时，也不代表总加载时间变短。控制试验使用旧候选响应注入；最终生产实现已撤回双 RAF，只保留实际 GPU 完成等待，复测结果另列，不混淆版本。

## 验证范围与真实限制

同一台 RTX 3080 Ti 电脑、Edge、固定森林种子 522。桌面 1180×720 高画质；手机为 844×390 触控和移动画质模拟，**不是安卓或 iOS 真机**。使用原生帧循环、真实声音和正常开始、升级、奖励、结算、再次远征按钮。

首轮候选完成桌面 300 秒＋60 秒＋60 秒连续三局、手机尺寸 90 秒以及蜃影三次闪避。夹具给予持续无敌、15 秒授予五种一阶技能、传送实际路线节点、150 秒额外增加 24 只怪物。首局首领按正常时间出现，短局通过夹具提前出现。这验证压力和资源生命周期，不代表自然难度通关。

| 首轮候选检查 | 结果 |
|---|---|
| 游玩窗口的新程序 | 0；基线首次经验球和阴影会新增 |
| 怪物声音缓存 | 在准备阶段生成；实战没有新增 |

音频缓存为怪物 PCM 4,692,608 字节、接触/武器 152,644 字节，另有原录音素材 10,905,600 字节。基线未记录 PCM 字节，不能把这些数值全部称为新增内存。

桌面首局 CPU 提交中位数/P95 为 4.2/8.8 → 3.7/7.0 毫秒；但候选期间原有动态像素比曾降至 0.9/0.95，基线未逐秒记录像素比，因此不能宣称这是相同渲染负荷下的 FPS 提升。手机尺寸同为比例 1，两版 CPU 中位数/P95 均为 3.6/6.9 毫秒。GPU 帧时间和屏幕实际呈现 FPS 未测。

首轮候选初次大厅就绪为 15.2 秒，基线约 15.1 秒，**本轮没有证实首次完整加载更快**。声音和特效准备有成本；连续两次重开单次观察缩短，但没有多轮统计。

仍未解决：首轮候选第二局记录到一次 187 毫秒长任务，没有新增程序或声音缓存，原因未定位；基线的周期长任务与一次 1.32 秒渲染调用间隔也未确定原因。三局没有发现线性资源增长，不等于无限时长无泄漏，不能保证所有设备完全不卡。

长测属于首轮候选；后续只改准备阶段，另做定向短测，不能称最终版重新完成全部七分钟流程。
